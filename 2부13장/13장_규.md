# 정리
- 도메인 특화 언어의 목표
  - 코드의 가독성과 유지 보수성을 가장 좋게 유지하는 것
- 깔끔한 API란?
  - 코드를 읽는 독자가 어떤 일이 벌어질지 명확하게 이해할 수 있어야 함: 이름과 개념을 잘 선택
  - 코드에 불필요한 구문이나 번잡한 준비 코드가 가능한 한 적어야 함: 간결함 중시
- 도메인 특화 언어
  - 메서드 호출만을 제공하는 API에 비해 더 표현력이 풍부해지고 사용하기 편함
  - 컴파일 시점에 모든 타입이 결정됨
  - 특정 과업 또는 영역에 초점을 맞추고 그 영역에 필요하지 않은 기능을 없앰
    - 참고) 범용 프로그래밍 언어: 컴퓨터로 풀 수 있는 모든 문제를 충분히 풀 수 있는 기능을 제공함
  - 제공하는 기능을 제한함으롰꺼 더 효율적으로 자신의 목표를 달성할 수 있음 (제작과정에서 고려할 점이 감소)
  - 범용 언어를 사용하는 경우보다 특정 영역에 대한 연산을 더 간결하게 기술할 수 있음
  - 선언적
    - 세부 실행 로직은 언어를 해석하는 엔진에 맡김
    - 엔진에 따라 자동 최적화를 수행, 효율적
  - 단점: 범용 언어로 만든 어플리케이션과 DSL을 같이 쓰기 어려움
    - DSL은 자체 문법이 있어서 다른 언어의 프로그램 안에 직접 포함시킬 수 없음
    - 컴파일 시점 검사 불가
    - 디버깅 어려움
    - IDE 기능 제공 어려움
  - 예시: SQL, 정규식
- 내부 DSL
  - 범용 언어로 작성된 프로그램의 일부
  - DSL의 핵심 장점을 유지하면서 주 언어를 별도의 문법으로 사용하는 것
- DSL vs 일반 API
  - DSL에는 구조(또는 문법)가 존재함
  - 메서드 호출 순서나 규칙을 정하는 문법이 별도로 존재한다는 뜻
- `kotlinx.html`
  - 직접 HTML 텍스트를 작성하지 않고 코틀린 코드로 만들어서 타입 안정성을 높일 수 있음
  - 내부에서 코틀린 코드를 원하는 대로 사용할 수 있음
- 수신 객체 타입
  - `StringBuilder.() -> Unit`
  - 확장 함수 타입
  - 확장 함수의 본문처럼 클래스 내부의 메서드를 마치 그 클래스 내부에서 호출하듯이 사용할 수 있음
- 빌더
  - 객체 계층 구조를 선언적으로 정의할 수 있음
  - 수신 객체 지정 람다를 사용하지 않을 경우 난잡해질 수 있음 (`it` 또는 람다의 파라미터명을 매번 지정해야 하므로)
  - 수신 객체 지정 람다를 통해 this를 일일히 쓰지 않아도 되어 깔끔함
- `@DslMarker` 어노테이션
  - 수신 객체 지정 람다가 다른 수신 객체 지정 람다 안에 들어가면 안쪽 람다에서 외부 람다에 정의된 수신 객체를 사용할 수 있음 (본인이 갖고있지 않은거면 외부 람다의 수신 객체에서 찾음)
  - 이 어노테이션을 사용하면 안쪽 람다에서 바깥쪽 람다의 수신 객체에 접근할 수 없고, 본인 것만 사용하도록 강제 가능
- `invoke` 관례
  - 임의의 객체를 함수처럼 호출할 수 있음
  - 참고) `get` 관례는 인덱스 연산자를 사용해 객체에 접근할 수 있음
  - `operator fun invoke`를 구현해야 함
  - 일반적인 람다 호출 역시 invoke 관례를 사용하는 것
- 중위 호출
  - `infix fun`
  - 코드에 쓰이는 기호의 수를 줄여 깔끔한 구문을 만들 수 있음
- 멤버 확장
  - 클래스 안에서 확장 함수와 확장 프로퍼티를 선언하는 기법
  - 선언된 클래스의 멤버이면서 확장하는 다른 타입의 멤버이기도 함
  - 멤버 요소들이 적용되는 범위를 제한하기 위해 사용
- 위임 프로퍼티
  - 자신의 API에 필요한 DSL을 만들어야 하고, 그 DSL을 깔끔하게 개선하고 싶을 떄 필요할 수 있음

# 궁금했던 것들

### 코틀린의 내부 DSL은 아무리 생각해도 결국 코틀린으로 선언한 클래스와 메서드가 아닌지? 외부와 연결을 도와주는 wrapper class를 DSL 이라고 따로 칭하는 것인지? '코틀린으로 DSL을 만들 수 있다'가 이 장의 핵심이 아니라 '코틀린은 이렇게 이쁜 문법을 제공한답니다'가 핵심인 것 같음
- 코드의 목적과 형태에 따라 DSL이라고 부르는 것임
- 코틀린의 syntactic sugar를 적극적으로 활용해서 "자바"와는 다르게 (더 간결하게) 표현할 수 있기 때문에 특별한 취급을 하는 것으로 추측됨

### `kotlinx.html`의 사용법은 '언럭키 jsx' 같은데, 코틀린에서 html을 지원하기 위해 jsx 같은 형태를 고려하지 않은 이유는 무엇일까?
- 코틀린의 주 목적이 html 생성이 아니라서? 넵
- jsx처럼 하려면 별도의 언어를 정의해야 해서? 넵
  - 확장 문법을 하려면 확장 컴파일러도 만들어야 하기 때문에 원래 언어가 더럽혀짐

### JSX도 일종의 DSL인가?
- JSX is a syntax extension for JavaScript
- 게임으로 치면 DLC 개념이라 DSL로 볼 수 있음
- 참고) 타입스크립트는 JS의 Fork 느낌이라 DSL이 아닌 독자적인 언어라고 볼 수 있음

### 수신 객체 지정 람다를 사용하면 코드 블록 내부에서 이름 결정 규칙을 바꿀 수 있다는 게 무슨 말인지?
- `this`가 가리키는 것이 수신 객체로 바뀐다는 뜻

### `kotlinx.html`에서 `+` 로 내부 텍스트를 정하는 것 같은데 이건 operator fun 을 만든것인지?
- 넵
- 가독성을 위해 텍스트 노드를 추가하는 메서드가 아닌 그냥 연산자로 만듦

### `KProperty2`가 멤버 확장을 가리킴. '콘텍스트 수신 객체'가 나오면 `KProperty3`도 나오는 것일까?
- 아니오
- 콘텍스트 수신 객체가 [있었는데](https://kotlinlang.org/docs/whatsnew1620.html#prototype-of-context-receivers-for-kotlin-jvm) 이제는 [없음](https://kotlinlang.org/docs/whatsnew2020.html#data-class-copy-function-to-have-the-same-visibility-as-constructor)
  - 수신 객체를 여러개 넣어버리면 누가 `this`인지가 모호해져서 헷갈려서 없앴다고 함
  - 그렇게 되어 수신 객체가 여러개인 경우의 수 자체가 없어져서 `KProperty3`이라는 게 나올 가능성도 없어짐
- 대신 [`context parameters`](https://github.com/Kotlin/KEEP/blob/context-parameters/proposals/context-parameters.md)라는걸 실험중

# 📌Question

### Q1) 책에서 DSL의 대표적인 예시로 SQL과 정규식을 들었는데요. SQL을 내부 DSL로 쓰는건 라이브러리를 보여줬는데, 왜 정규식을 코틀린 내부 DSL로 사용하는 예시는 들지 않았을까요?
- 정규식을 dsl로 사용하면 구조가 드러나는 것은 좋지만, 코드의 길이가 길어질 가능성이 높음
- 일반적으로 정규식을 크게 어려운 형태로 사용하는 경우가 많지 않음
- 질문의 의도: 내부 DSL이 너무 좋다고만 써놓아서 그렇지 않은 예시를 생각해 보았습니다

### Q2) 빌더를 구현할 때 수신 객체 지정 람다를 사용하는 것의 장점과 주의할 점이 있을까요?
- 수신 객체 지정 람다를 사용하지 않을 경우 난잡해질 수 있음 (`it` 또는 람다의 파라미터명을 매번 지정해야 하므로)
- 수신 객체 지정 람다를 통해 this를 일일히 쓰지 않아도 되어 깔끔함
- 다만 수신 객체 지정 람다가 다른 수신 객체 지정 람다 안에 들어가면 안쪽 람다에서 외부 람다에 정의된 수신 객체를 사용할 수 있기 떄문에 `@DslMarker` 사용을 권장함

### Q1) 수신 객체 지정 람다 T.() -> R과 일반 람다 (T) -> R은 컴파일러 입장에서 같은 타입일까요?
- 개발자 입장에서는 두 개가 다른 타입으로 인식됨
- 컴파일러 내부에서는 둘 다 `Function1<T, R>`로 취급함
- 둘 사이에 오버로딩은 불가능
  ```kotlin
  // Conflicting overloads: fun process(block: String.() -> Unit): Unit
  // Conflicting overloads: fun process(block: (String) -> Unit): Unit
  fun process(block: (String) -> Unit) {}
  fun process(block: String.() -> Unit) {}
  ```

### Q2) @DslMarker가 막는 것은 무엇이고, 막지 않으면 무슨 일이 일어날까요
- 수신 객체 지정 람다가 다른 수신 객체 지정 람다 안에 들어가면 안쪽 람다에서 외부 람다에 정의된 수신 객체를 사용할 수 있음 (본인이 갖고있지 않은거면 외부 람다의 수신 객체에서 찾음)
- 이 어노테이션을 사용하면 안쪽 람다에서 바깥쪽 람다의 수신 객체에 접근할 수 없고, 본인 것만 사용하도록 강제 가능

### Q1) 일반 API와 DSL을 구분 짓는 가장 핵심적인 차이는 무엇일까요?
- DSL은 언어이고 일반 API는 언어를 사용해서 만든 부산물이기 떄문에 DSL에는 문법(syntax)이 존재함

### Q2) 외부 DSL(예: 순수 SQL)과 비교했을 때, 코틀린 내부 DSL이 가지는 "컴파일 시점 검증"의 강력함은 구체적으로 어떤 실수를 방지해 주나요?
- 외부 DSL은 일반적으로 text 형태로 활용하게 되어 컴파일 시점에 오류를 감지할 수 없음
- 내부 DSL은 코틀린 타입 시스템을 통해 본인의 syntax를 구현한 상태이기 떄문에, 코틀린 컴파일러를 통해 미리 검사해서 런타임에 문제가 생기는 것을 막을 수 있음
