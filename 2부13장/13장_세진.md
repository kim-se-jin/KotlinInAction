# 13장 DSL 만들기

## 13.1 API에서 DSL로

### 영역 특화 언어 (DSL)

범용 프로그래밍 언어(코틀린, 자바)와 대비되는 개념. 특정 도메인 문제만 풀도록 설계된 언어

- 외부 DSL: 독자적인 문법을 가짐. SQL, 정규식 등. 호스트 언어와 분리
- 내부 DSL: 호스트 언어 문법 안에서 도메인에 특화된 API로 표현. 별도 파서 불필요
- DSL은 보통 선언적, "무엇을 할지"만 기술하고 "어떻게 할지"는 라이브러리가 결정

### 내부 DSL의 예

명령형 API

```kotlin
StringBuilder().apply {
    append("<html>")
    append("<body>")
    append("hello")
    append("</body>")
    append("</html>")
}
```

DSL 스타일

```kotlin
html {
    body {
        +"hello"
    }
}
```

### DSL의 구조

일반 API 호출은 일련의 메서드 호출이 평면적으로 나열. DSL은 람다 중첩, 메서드 체이닝으로 구조를 만듦.

```kotlin
// 일반 API
project.dependencies.add("compile", "junit:junit:4.11")

// DSL
dependencies {
    compile("junit:junit:4.11")
}
```

DSL은 같은 컨텍스트에서 여러 호출을 묶을 수 있음. 명령형 API는 매번 같은 객체를 다시 명시해야 함.

### 내부 DSL로 HTML 만들기

```kotlin
fun createSimpleTable() = createHTML().table {
    tr {
        td { +"cell" }
    }
}
```

장점

- 타입 안전성. 잘못된 위치에 잘못된 태그를 넣으면 컴파일 에러
- 코틀린 코드의 모든 기능 사용 가능 (조건문, 반복문, 변수)

```kotlin
fun createAnotherTable() = createHTML().table {
    val numbers = mapOf(1 to "one", 2 to "two")
    for ((num, string) in numbers) {
        tr {
            td { +"$num" }
            td { +string }
        }
    }
}
```

## 13.2 구조화된 API 구축 - 수신 객체 지정 람다

### 수신 객체 지정 람다와 확장 함수 타입

DSL의 핵심 메커니즘. 람다 안에서 특정 객체를 `this`로 사용할 수 있게 함.

일반 람다 타입

```kotlin
val sum: (Int, Int) -> Int = { a, b -> a + b }
```

확장 함수 타입(수신 객체 지정 람다 타입)

```kotlin
val appendExcl: StringBuilder.() -> Unit = { append("!") }
//              ↑
//              수신 객체 타입

val sb = StringBuilder("Hi")
sb.appendExcl()   // 확장 함수처럼 호출
appendExcl(sb)    // 일반 함수처럼도 호출 가능
```

이 타입은 `StringBuilder`의 메서드처럼 동작하는 람다. 람다 내부에서 `this`는 `StringBuilder`

`buildString` 표준 라이브러리 함수가 이 패턴을 사용

```kotlin
fun buildString(action: StringBuilder.() -> Unit): String {
    val sb = StringBuilder()
    sb.action()
    return sb.toString()
}

val s = buildString {
    append("Hello, ")    // this.append, this는 StringBuilder
    append("World!")
}
```

`apply`, `with`, `run` 등 표준 스코프 함수가 모두 이 메커니즘 위에 동작

```kotlin
inline fun <T> T.apply(block: T.() -> Unit): T {
    block()
    return this
}
```

### @DslMarker

중첩된 빌더에서 외부 수신 객체에 실수로 접근하는 것을 막음.

```kotlin
table {
    tr {
        tr { }   // 의도치 않게 호출 가능. 외부 TABLE의 tr이 보임
    }
}
```

`@DslMarker` 어노테이션을 만들고 빌더 클래스에 붙이면 중첩된 람다에서 외부 수신 객체의 멤버에 직접 접근 불가

```kotlin
@DslMarker
annotation class HtmlTagMarker

@HtmlTagMarker
open class Tag(val name: String) { ... }
```

## 13.3 invoke 관례

`invoke`는 함수 호출처럼 보이게 만드는 연산자

- 임의의 클래스에 `invoke`를 정의해서 인스턴스를 함수처럼 호출 가능

### invoke 관례 기본

```kotlin
class Greeter(val greeting: String) {
    operator fun invoke(name: String) {
        println("$greeting, $name!")
    }
}

val bavarianGreeter = Greeter("Servus")
bavarianGreeter("Dmitry")   // Servus, Dmitry!
```

- `bavarianGreeter("Dmitry")`는 `bavarianGreeter.invoke("Dmitry")`로 컴파일
  - 함수 타입과 동일한 메커니즘.
  - 차이점!!! 함수 타입은 `Function0`~`Function22` 인터페이스를 자동으로 구현하는 것이고, 임의 클래스의 `invoke`는 직접 `operator` 키워드로 정의한다고 함

### 오버로드도 가능

`invoke`는 일반 메서드처럼 시그니처가 다른 여러 버전을 만들 수 있음.

```kotlin
class Greeter {
    operator fun invoke(name: String) { ... }
    operator fun invoke(name: String, times: Int) { ... }
    operator fun invoke(names: List<String>) { ... }
}

val g = Greeter()
g("Alice")
g("Bob", 3)
g(listOf("X", "Y"))
```

- 같은 인스턴스를 다양한 시그니처로 호출 가능

### invoke와 고차 함수의 결합

함수 타입을 받는 자리에 함수 타입을 구현한 클래스를 넘기는 패턴

```kotlin
data class Issue(
    val id: String, val project: String, val type: String,
    val priority: String, val description: String
)

class ImportantIssuesPredicate(val project: String) : (Issue) -> Boolean {
    override fun invoke(issue: Issue): Boolean {
        return issue.project == project && issue.isImportant()
    }
    private fun Issue.isImportant(): Boolean {
        return type == "Bug" && (priority == "Major" || priority == "Critical")
    }
}

val issues = listOf(...)
val predicate = ImportantIssuesPredicate("IDEA")
for (issue in issues.filter(predicate)) {
    println(issue)
}
```

- `ImportantIssuesPredicate`가 `(Issue) -> Boolean`을 구현했기 때문에 `filter`에 그대로 넘길 수 있다
  - 람다 한 줄로 쓸 수도 있지만, 클래스로 만들면 복잡한 로직을 메서드로 분해할 수 있고 테스트도 쉬워지므로

### DSL의 invoke 사용 - Gradle dependenvices

Gradle DSL이 두 가지 호출 형태를 동시에 지원 가능한 이유는 `invoke`

```kotlin
// 형태 1. 람다 블록
dependencies {
    compile("junit:junit:4.11")
}

// 형태 2. 직접 호출
dependencies.compile("junit:junit:4.11")
```

### invoke 쓸 때 주의

- `operator` 키워드 필수
- 너무 남용하면 코드 가독성 저하. 호출자가 그 객체가 함수처럼 호출 가능한지 모를 수 있음

## 13.4 실전 코틀린 DSL

### 중위 호출 연쇄 - should

코테스트(Kotest) 같은 테스트 프레임워크의 DSL.

```kotlin
"kotlin" should startWith("kot")
```

`should`가 중위 함수(infix function)로 선언되어 아래와 같이 구현되어 있는 것.

```kotlin
infix fun <T> T.should(matcher: Matcher<T>) = matcher.test(this)
```

중위 함수 조건

- 멤버 함수 또는 확장 함수
- 파라미터 하나
- `infix` 키워드

`startWith`는 `Matcher` 객체를 만드는 함수

```kotlin
interface Matcher<T> {
    fun test(value: T)
}

fun startWith(prefix: String): Matcher<String> = object : Matcher<String> {
    override fun test(value: String) {
        if (!value.startsWith(prefix)) throw AssertionError(...)
    }
}
```

중위 호출과 객체 매처를 조합하면 자연어처럼 읽힌다!

### 원시 타입에 대한 확장 함수 - 날짜 처리

```kotlin
val yesterday = 1.days.ago
val tomorrow = 1.days.fromNow
```

- `Int`에 확장 프로퍼티 `days`가 정의되어 있고 `days`가 반환하는 타입에 `ago`, `fromNow` 확장 프로퍼티가 있음.
  - 코틀린에서는 기본 타입에도 확장 함수/프로퍼티를 정의할 수 있어서 가능
  - 자바는 불가능

### 멤버 확장 함수 - SQL DSL

Exposed 라이브러리의 SQL DSL.

```kotlin
object Country : Table() {
    val id = integer("id").autoIncrement().primaryKey()
    val name = varchar("name", 50)
}
```

`integer`, `varchar`는 `Table`의 멤버 함수. `autoIncrement`, `primaryKey`는 그 반환값에 대한 멤버 확장 함수.

```kotlin
class Table {
    fun integer(name: String): Column<Int>
    fun varchar(name: String, length: Int): Column<String>
    
    fun <T> Column<T>.primaryKey(): Column<T> { ... }
    fun Column<Int>.autoIncrement(): Column<Int> { ... }
}
```

멤버 확장 함수 특징

- 클래스 내부에 정의되어 그 클래스 인스턴스를 통해서만 접근 가능
- 두 개의 수신 객체를 가짐. 디스패치 수신 객체(`Table`)와 확장 수신 객체(`Column`)
- 스코프 제한 효과. `autoIncrement`는 `Table` 컨텍스트 안에서만 호출 가능
