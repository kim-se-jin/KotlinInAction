## 13.1 API에서 DSL로: 표현력이 좋은 커스텀 코드 구조 만들기

DSL이 해결하려는 문제 : 코드의 가독성과 유지보수성

- 코드를 읽는 독자가 어떤 일이 벌어질지 명확핳게 이해할 수 있어야 한다. 이름과 개념을 잘 선택하여 목적 달성 가능
- 코드에 불필요한 구문이나 번잡한 준비 코드가 적어야 한다.

코틀린의 확장 함수, 중위 함수 호출, 람다의 it, 연산자 오버로딩 등의 기법을 사용해 깔끔한 API작성 가능

## 13.1.1 도메인 특화 언어

가장 익숙한 DSL은 SQL 정규식일 것이다.

SQL 문장은 첫 키워드가 수행하려는 연산의 종류 (SELECT, INSERT, …) 를 지정하고 연산은 처리해야 할 작업에 맞춰 서로 다른 문법과 키워드를 제공한다.

디비 엔진은 쿼리가 문법에 맞는지 확인해서 실행계획을 세우고 실제로 데이터를 추출한다.

DSL은 선언적이며 범용 프로그래밍 언어는 보통 명령적이다.

DSL은 범용 언어로 만든 호스트 어플리케이션과 DSL을 함꼐 조합하기 어렵다는 단점이 있다.

DSL은 자체 문법이 있기 때문에 다른 언어의 프로그램 안에 직접 포함시킬 수 없다.

즉 컴파일 시점 검증, 디버깅, IDE의 도움등을 받기 어렵다.

이를 해결하기 위해 코틀린은 내부적으로 DSL을 만들 수 있께 한다.

## 13.1.2 내부 DSL은 프로그램의 나머지 부분과 매끄럽게 통합된다.

외부 DSL : 독립 적인 문법 구조

내부 DSL : 범용 언어로 작성된 프로그램의 일부, 범용 언어와 동일한 문법을 사용한다.

ex) 쿼리 수행 예제

```sql
SELECTCountry.name, COUNT(Customer.id)
	FROM Country
INNER JOIN CUSTOMER
	ON Country.id = Customer.country_id
	GROUP BY Country.name
	ORDER BY COUNT(Customer.id) DESC
	LIMIT 1
```

```kotlin
// 코틀린 EXPOSED
(Country innerJoin Customer)
	.slice(Country.name, Count(Customer.id))
	.selectAll()
	.groupBy(Country.name)
	.orderBy(Count(Customer.id), order = SortOrder.DESC)
	.limit(1)
```

코틀린의 메소드를 체이닝 한 것 뿐이다.

## 13.1.3 DSL의 구조

DSL과 일반 API사이에 잘 정의된 경계는 없다. 그 둘의 평가는 주관적이다.

DSL에만 존재하는 특징은 바로 **구조** 와 **문법**이다

DSL의 메서드 호출은 DSL 문법에 의해 정해지는 구조에 속한다.

DSL에서는 여러 함수 호출을 조합해서 연산을 만들며 타입검사기는 여러 함수 호출이 바르게 조합됐는지 검사한다.

함수 이름은 보통 동사 역할을 하고 함수 인자는 명사 역할을 한다.

그레이들 빌드 스크립트 또한 코틀린 DSL의 예제이다.

메서드 호출 연쇄는 DSL 구조를 만드는 또 다른 방법이다.

```kotlin
str should startWith("kot")

assertTrue(str.startWith("kot"))
```

## 13.2 구조화된 API 구축: DSL에서 수신 객체 지정 람다 사용

수신 객체 지정 람다 : 수신객체가 정해져 있는 람다. 즉 사용할 수 있는 곳이 한정적.

## 13.2.1 수신 객체 지정 람다와 확장 함수 타입

buildString 함수가 어떻게 구현됐는지 보자

```kotlin
fun buildString(
	builderAction: (StringBuilder) -> Unit // 함수 타입인 파라미터를 정의
): String {
	val sb = StringBuilder()
	buildderAction(sb)
	return sb.toString()
}

fun main(){
	val s = buildString {
		it.append("Hello, ")
		it.append("World!")
	}
	print(s) 
}
```

람다 안에서 it을 사용해 StringBuilder를 참조하는 것이 중복이다.

```kotlin
fun buildString(
	builderAction: StringBuilder.() -> Unit // 수신 객체 지정 함수 타입의 파라미터를 선언
): String {
	val sb = StringBuilder()
	sb.buildAction()
	return sb.toString()
}

fun main(){
	val s = buildString {
		append("Hello, ")
		append("World!")
	}
	print(s) 
}
```

(StringBuilder) → Unit 을 StringBuilder.() → Unit 으로 바꿨다. 이런 타입을 수신 객체 타입이라 부르며, 람다에 전달되는 그런 타입의 객체를 수신 객체라고 부른다.

```kotlin
// 수신 객체 타입 : String
// 파라미터 타입 : (Int, Int)
// 반환 타입 : Unit
String.(Int, Int) -> Unit

```

왜 확장 함수 타입일까? 확장 함수의 본문에서는 확장 대상 클래스에 정의된 메서드를 마치 클래스 내부에서 호출하듯이 사용할수 있었다. 그렇기에 it이 생략가능한 것이다.

```kotlin
buildString {
	this.remove("World!") // this : StringBuilder() 인스턴스를 의미
}
```

수신 객체 지정 람다를 변수에 저장하기

```kotlin
val appendExcl: StringBUilder.() -> Unit =
	{ this.append("!") }
	
fun main() {
	val sb = StringBuilder("Hi")
	sb.appendExcl()
	println(sb) // Hi!
	
	println(buildString(appendExcl)) // !
}
```

표준 라이브러리의 buildString 구현은 리스트 13.2보다 더 짧다. builderAction을 명시적으로 호출하는 대신 apply 함수에게 인자로 넘긴다.

```kotlin
fun buildString(builderAction: StringBuilder.() -> Unit): String = 
	StringBuilder().apply(builderAction).toString()
```

apply 함수는 인자로 받은 람다나 함수를 호출하면서 자신의 수신 객체를 람다나 함수의 암시적 수신 객체로 사용한다.

## 13.2.2 수신 객체 지정 람다를 HTML 빌더 안에 사용

```kotlin
open class Tag

class Table : Tag {
	fun tr(init : TR.() -> Unit)
}

class TR : Tag {
	fun td(init : TD.() -> Unit)
}

class TD : Tag

// Table { TR { TD } }
```

TABLE, TR, TD는 모두 HTML 생성 코드에 명시적으로 나타나면 안 되는 유틸리티 클래스다. 따라서 이름을 **모두 대문자**로 만들어서 일반 클래스와 구분한다.

HTML 빌더 호출의 수신 객체를 명시한 코드

```kotlin
fun createSimpleTable() = createHTML().table {
	this@table.tr {
		(this@tr).td {
			+"cell" // 암시적으로 this@td를 사용할 수 있다
		}
	}

}
```

문제는 외부 람다에 정의된 수신 객체를 사용할 수 있다는 것이다.

이를 막기 위해 코틀린은 `@DslMaker` 어노테이션을 사용해 내포된 람다에서 외부 람다의 수신 객체에 접근하지 못하게 제한한다.

```kotlin
@DslMaker
annotation class HtmlTagMaker

@HtmlTagMaker
open class Tag
```

이렇게 사용하면 tr, td 안에서 table을 직접 호출하지 못한다.

만약 사용하게 되면 컴파일 에러가 발생한다.

전체 HTML은 어떻게 만드나?

```kotlin
@DslMaker
annotation class HtmlTagMaker

@HtmlTagMaker
open class Tag(val name: String) {
	private val children = mutableListOf<Tag>() // 모든 내포된 태그를 저장한다.
	
	protected fun <T : Tag> doInit(child: T, init: T.() -> Unit) {
		child.init()
		children.add(child)
	}
	
	override fun to String() = ""
}

fun table(init: TABLE.() -> Unit) = TABLE().apply(init)

class TABLE : Tag("table") {
	fun tr(init: TR.() -> Unit) = doInit(TR(), init)
}

class TR : Tag("tr") {
	fun tr(init: TD.() -> Unit) = doInit(TD(), init)
}

class TD : Tag("td")

fun createTable() = 
	table {
		tr {
			td {}
		}
	}

fun main() {
	println(createTable())
}
```

도우미 함수를 사용해 목차가 있는 페이지 만들기

```kotlin
fun buildBookList() = createHTML().body {
	listWithToc {
		item("","")
		item("","")
		item("","")

@HtmlTagMaker
class LISTWITHTOC {
	val entries = mutableListOf<Pair<String, String>>()
	fun item(headline: String, body: String) {
		entries += headline to body

}

```

## 13.3 invoke 관례를 사용해 더 유연하게 블록 내포시키기

invoke 관례를 사용하면 객체를 함수처럼 호출할 수 있다.

## 13.3.1 invoke 관례를 사용해 더 유연하게 블록 내포시키기

```kotlin
class Greeter(val greeting: String) {
	operator fun invoke(name: String) {
		println("$greeting, $name!")
	}
}

fun main() {
	val bavarianGreeter = Greeter("Servus")
	bavarianGreeter("Dmitry")
	// Servus, Dmitry!
}
```

invoke는 컴파일 시점에는 interface Function으로 컴파일 된다.

## 13.3.2 DSL의 invoke 관례: 그레이들 의존 관계 선언

gradle 설정에서 dependencies 는 다음과 같이 선언 가능하다

```kotlin
dependencies.implementation("")
dependencies{
	implementation("")
}
```

첫번째는 implementation 메서드를 호출한다.

두번째는 dependencies 안에 람다를 받는 invoke 메서드를 정의한 방식이다.
