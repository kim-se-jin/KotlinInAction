# 정리
- 동시성
  - 여러 작업을 동시에 실행하는 것
  - 모든 작업을 물리적으로 함께 실행할 필요는 없음
  - 코어가 하나뿐인 시스템에서도 여러 동시성 태스크를 계속 전환해 가는 방법으로 동시성 가능
- 병렬성
  - 여러 작업을 여러 CPU 코어에서 물리적으로 동시에 실행하는 것
- `thread`
  - 새로운 스레드를 시작
  - 어플리케이션 반응성 증가
  - 여러 코어에 작업을 분산시켜 현대적 시스템을 더 효율적으로 사용
  - 스레드 할당과 전환에 비용이 듦
  - 스레드가 작업 실행 중에는 block됨
  - 새로운 스레드 생성은 신중하게 진행해야 하며, 잠깐 사용하는 용도가 아님
- 코루틴
  - 비동기적으로 실행되는 non-blocking 동시성 코드를 표현
  - 스레드에 대한 경량 추상화
  - 일시 중단 가능한 계산의 인스턴스
  - 생성하고 관리하는 비용이 저렴함
  - 자원을 블록하지 않고 실행을 일시 중단한 후 나중에 재개하여 블로킹 스레드보다 효율적
  - 구조화된 동시성: 동시 작업의 구조와 계층을 확립하며, 취소 및 오류 처리를 위한 매커니즘 제공
  - 컴파일러
    - 코루틴의 일시 중단, 재개 등에 필요한 코드를 생성
    - 일시 중단 함수의 코드를 컴파일 시점에 변경
  - runtime
    - 코루틴이 일시 중단될 때 해당 시점의 상태 정보를 메모리에 저장함
    - 이 정보를 바탕으로 나중에 실행을 복구하고 재개
- `suspend`
  - 함수가 실행을 잠시 멈출 수도 있다는 뜻
  - 일시 중단은 기저 스레드를 블록하지 않음
  - 같은 스레드에서 다른 코드를 실행 가능
  - 코드 작성은 순차적으로 하지만, 실제 동작은 블로킹 코드와는 다름
- 다른 비동기 처리 방식
  - callback
    - callback hell의 단점이 너무 큼
  - future
    - 함수의 반환 타입을 변경해야 함
  - 반응형 스트림(Rx)
    - 함수 시그니처를 바꿔야 함
- 일시 중단 함수 호출
  - 일시 중단 함수는 실행을 일시 중단할 수 있는 코드 블록 안에서만 실행 가능
  - 프로그램의 main 함수를 suspend 로 만들기
    - 이러기에는 쉽지 않은 경우가 많음
  - 코루틴 빌더 사용하기
    - 코루틴을 생성함
    - 일시 중단 함수를 호출하기 위한 일반적인 진입점 
- `runBlocking`
  - 해당 코루틴이 완료될 때까지 현재 스레드를 블록시킴
  - 코루틴 안에서 시작되는 다른 자식 코루틴들은 스레드를 블록시키지 않음
- `launch`
  - 새로운 자식 코루틴을 시작
  - fire-and-forget 방식에 적합
  - 코루틴 내부에서 값을 반환하는 것이 쉽지 않음
  - side effect 작업에 적합
- `async`
  - 반환 타입: `Deferred<T>` 인스턴스
  - `await` 함수로 결과를 기다릴 수 있음
    - 호출 시 Deferred의 결괏값이 사용 가능해질 때까지 루트 코루틴을 일시 중단
  - Future, Promise 와 같은 개념: 아직 사용할 수 없는 값을 나타냄
- Dispatcher
  - 코루틴을 실행할 스레드를 결정함
  - 코루틴을 특정 스레드로 제한하거나 스레드 풀에 분산시킴
  - 코루틴은 특정 스레드에 고정되지 않으므로, 일시 중단할 떄의 스레드와 재개할 때의 스레드가 다를 수 있음
  - `Dispatchers.Default`
    - CPU 코어 수만큼의 스레드로 구성된 스레드 풀을 기반으로 함
    - 가장 일반적인 디스패처
  - `Dispatchers.Main`
    - UI 스레드나 메인 스레드와 같이 특정한 스레드에서만 실행해야 하는 작업이 있는 경우
  - `Dispatchers.IO`
    - 서드파티 라이브러리가 코루틴을 염두에 두고 만들어지지 않은 경우
    - CPU 코어 수에 구애받지 않아야 하는 경우
    - 자동으로 확장되는 스레드풀에서 실행됨
- 스레드 풀
  - 스레드 집합을 관리
  - 작업이 실행될 때마다 새 스레드를 할당하는 대신, 일정한 수의 스레드를 유지하면서 내부 로직에 따라 들어오는 작업을 분배
- `withContext`
  - 이미 실행 중인 코루틴 내부에서 디스패처를 바꿀 떄 사용
- thread safe
  - 한 코루틴은 항상 순차적으로 실행됨
  - 단일 코루틴에 연관된 데이터가 전형적인 동기화 문제를 일으키지 않음
  - 여러 코루틴이 같은 데이터를 건드리는 경우 문제 발생 가능
  - 스레드와 마찬가지로 동기화나 잠금 처리를 해야 함
  - 해결책
    - lock을 걸기
    - 병렬 변경을 위한 원자적이고 thread-safe 한 자료구조 사용
    - 코루틴을 단일 스레드 디스패처에서 실행하도록 제한
- `CoroutineContext`
  - 코루틴에 관한 여러 정보를 담고 있음
    - 디스패처, Job, 메타데이터 등등
  - 어떤 일시 중단 함수 안에서든 `coroutineContext`라는 속성에 접근 가능
  - 이 속성은 컴파일러 고유 기능으로, 실제 구현은 컴파일러가 알아서 잘 처리함

# 궁금했던 것들

### 코루틴의 일시 중단 지점은 누가 어떻게 만드는가?
- 컴파일러가 일시 중단 함수 내부의 코드를 일종의 state machine으로 만듦
- 일반적으로 일시 중단 함수 호출 지점을 기준으로 상태를 나눈다

### 왜 UI는 특정 스레드에서만 실행해야 하는가?
- 일반적으로 사용자와의 티키타카는 명확한 순서가 존재함
- UI를 thread-safe 하게 만들기 쉽지 않음
- 여러 스레드에서 작업할 떄 race condition

# 📌Question

### Q1) `runBlocking`의 특징과 사용하는 이유는 무엇일까요? (p.629)
- 특징: 해당 코루틴이 완료될 때까지 현재 스레드를 블록시킴
- 일시 중단 함수가 아닌 함수에서 최초로 코루틴을 시작하기 위해 사용함

### Q2) 다른 동시성 처리 방법과 비교했을 때 코루틴이 갖는 장점이 무엇인가요? (p.624)
- callback, promise, future, rx 등과 다르게 함수의 시그니처를 바꿀 필요가 없음
- 코루틴 내부에서 코드 작성 자체는 기존과 동일하게 순차적인 방식으로 쓰면 되어서, 기존 코드에 코루틴을 붙이는 리팩토링 비용이 크지 않음

### Q1) 코루틴의 실행 기록은 JVM 메모리 중 어느 영역에 저장되고 있을까요?
- 컴파일러는 일시 중단 함수를 state machine 으로 만드는데, 이떄 상태를 기억하기 위해 `Continuation` 인터페이스를 구현하는 클래스의 인스턴스를 사용
- `Continuation` 구현체의 인스턴스는 힙 메모리에 저장됨
    
### Q2) Dispatcher를 커스텀하게 사용할 경우가 있을까요?
- 디스패처가 하는 일이 코루틴이 어느 스레드에 들어갈 것인지 관리하는 것
- 가장 특수한 경우는 Dispatchers.Main 이 커버하고 있다고 생각합니다
- 특정 작업을 반드시 특정 스레드풀에서만 실행하여, 다른 작업들에 영향을 주고 싶지 않다면 사용할 수 있을 것 같음 (`newFixedThreadPool`)
