
경량 쓰레드인 코루틴 OS의 쓰레드가 아닌 프로그램 안에서 컨텍스트 스위칭을 하여 Blocking을 막고 자원을 효율적으로 사용한다.

## 14.1 동시성과 병렬성

동시성 : 코드를 여러 부분으로 나눠서 수행할 수 있는 능력

병렬성 : 여러 작업을 여러 CPU 코어에서 물리적으로 동시에 실행하는 것

## 14.2 코틀린의 동시성 처리 방법: 일시 중단 함수와 코루틴

코루틴은 비동기적으로 실행되는 넌블록킹 코드를 우아하게 사용할 수 있다.

suspend 함수를 사용하면 일반 함수와 같이 코드를 작성하지만 Non Blocking으로 쓰레드 자원을 코루틴을 활용해 효율적으로 사용할 수 있다.

## 14.3 스레드와 코루틴 비교

애플리케이션에서 스레드를 사용하는데는 비용이 든다. JVM이 생성하는 스레드는 일반적으로 OS가 관리하는 스레드이며, 이러한 스레드를 생성하고 관리하는 것도 비용이다.

각 스레드는 몇 메가바이트의 메모리를 할당받아야 하고 Context Switching비용이 실제로 커널단에서 발생한다.

추가로 스레드는 Blocking되면 사용하지 못하고 멈춘다. 또한 취소가 불가능하다. (인터럽트는 가능)

코루틴 : 스레드의 대안으로 실제로 스레드를 사용하지만 스레드를 효율적으로 사용하기 위해 JVM위에서 동작하는 경량 스레드다.

- 노트북에서도 100,000개 이상 실행 가능
- 시스템 자원을 Block 시키지 않고 중단된 지점부터 재개 가능 (I/O 작업 등)
- 구조화된 동시성이라는 개념을 통해 동시 작업의 구조와 계층을 확립하며, 취소 및 오류 처리를 위한 메커니즘을 제공.
- 코루틴은 하나 이상의 JVM 스레드에서 실행됨

## 14.4 잠시 멈출 수 있는 함수: 일시 중단 함수

코틀린 코루틴이 좋은 점은 기존 코드 ‘형태’를 변경할 필요가 없다는 점이다.

## 14.4.1 일시 중단 함수를 사용한 코드는 순차적으로 보인다.

```kotlin
suspend fun login(cre: Cre): UserId
suspend fun loadUserData(userId: UserId): UserData
suspend fun showData(data: UserData)

suspend fun showUserInfo(cred: Cred) {
	val userId = login(cred)
	val userData = loadUserData(userId)
	showData(userData)
}
```

여기서 login과 loadUserData는 suspend함수이기 때문에 코루틴 안에서 순차적으로 실행되지만 스레드가 Blocking 당하지 않는다.

가령 login안에 Blocking 되는 작업이 있다면 그동안 코루틴은 다른 작업을 하러 간다.

## 14.5 코루틴을 다른 접근 방법과 비교

콜백, RxJava, Future 와 비교하였을 때?

콜백은 체이닝을 해주어야 하기 때문에 코드가 복잡하다. 개행이 많이 이루어짐.

추가로 사람이 읽기 쉽지 않다. 인지적 부가비용도 존재한다.

하지만 코루틴에서는 함수에 suspend 변경자만 추가해주면 된다. Future와 마찬가지로 코루틴은 Deffered라는 값을 사용해 결과를 받을 수도 있다.

## 14.5.1 일시 중단 함수 호출

일시 중단 함수는 실행을 일시 중단할 수 있기 때문에 아무 곳에서나 호출할 수 없다.

- 일시 중단 함수안에서 호출 가능
- 코루틴 빌더 함수에서 호출 가능

## 14.6 코루틴의 세계로 들어가기: 코루틴 빌더

일시 중단 함수를 실행하며 코루틴이 시작될 수 있는 빌더가 있다. 

- runBlocking : 블로킹 코드와 일시 중단 함수의 세계를 연결해 준다.
- launch : 값을 반환하지 않는 새로운 코루틴을 시작할 떄 쓰인다.
- async : 비동기적으로 값을 계산할 때 쓰인다.

## 14.6.1 일반 코드에서 코루틴의 세계로: runBlocking

```kotlin
suspend fun doSomeSlow() {
	delay(500.milliseconds)
	println("I'm done")
}

fun main() = runBlocking {
	doSomeSlow()
}
```

일반 함수에서 runBlocking을 사용해서 일시 중단 함수를 호출할 수 있다. 

쓰레드는 main()을 호출한 쓰레드가 사용된다. (기본)

## 14.6.2 발사 후 망각 코루틴 생성: launch 함수

```kotlin
private var zeroTime = System.currentTimeMillis()
fun log(message: Any?) = println(zeroTime + " " + Thread.currentThread().name)

fun main() = runBlocking {
	log("First")
	launch{
		log("second")
		delay(100.millis) // 일시 중단 지점
		log("second resume")
	}
	launch{
		log("thrid")
	}
	log("first laucnh 2 coroutins")
}

// c1 First -> c1 first launch 2 coroutines -> c2 second -> c3 third -> c2 second resume
```

<aside>
💡

**일시 중단된 코루틴은 어디로 가는가?**

**컴파일러가** 코루틴의 일시 중단하고 재개하며, **스케줄링하는** 데 필요한 지원 코드를 생성한다.

일시 중단 함수의 코드는 컴파일 시점에 변환되고 실행 시점에 코루틴이 일시 중단될 때 해당 시점의 **상태 정보가 메모리에 저장**된다.

</aside>

## 14.6.3 대기 가능한 연산: async 빌더

async 함수는 결과를 받을 수 있는 Deferred<T> 인스턴스를 반환해준다. await함수를 사용해 얻을 수 있음.

```kotlin
suspend fun slowAddNumber(a: Int, b: Int): Int {
	log("wait" + a)
	delay(100.millis * a)
	return a + b
}

fun main() = runBlocking {
	log("start async compute")
	val firstDeffered = async { slowAddNumber(2, 2) }
	val secondDeffered = async { slowAddNumber(4, 4) }
	log("wait for the deffered value")
	log("first : ${firstDeffered.wait()}")
	log("second: ${secondDeffered.wait()}")
}

// start
// wait for deffered value
// wait 2
// wait 4
// first: 4
// second: 16
```

wait을 사용한다고 코루틴이 중단되는게 아니라 결과값이 사용가능해질 때 코루틴을 다시 할당받는다.

Deffered : 미래에 언젠가는 값을 알게 될 것이라는 약속, 연기된 계산 결과값.

| 빌더 | 반환값 | 쓰임 |
| --- | --- | --- |
| runBlocking | 람다가 계산한 값 | 블로킹 코드와 넌블로킹 코드 연결 |
| launch | Job | 발사 후 망각 코루틴 시작(부수 효과 있음) |
| async | Deferred<T> | 값을 비동기로 계산(값을 기다릴 수 있음) |

코루틴은 스레드 위에 만들어진 추상화다. 그렇다면 실제로 어떤 쓰레드에서 수행될까? 

사용되는 쓰레드를 제어할 수 있게 코루틴에서는 Dispatcher를 사용한다.

## 14.7 어디서 코드를 실행할지 정하기: 디스패처

코루틴은 특정 스레드풀 혹은 스레드에서 실행되게 제한시킬 수 있다.

## 14.7.1 디스패처 선택

코루틴은 기본적으로 부모 코루틴에서 디스패처를 상속받는다. 그렇기에 명시적으로 Dispatcher를 지정할 필요가 없다.

다중 스레드를 사용하는 범용 디스패처: Dispatchers.Default

가장 일반적인 디스패처로 CPU코어 수만큼의 스레드로 구성된 스레드 풀을 기반으로 한다.

그렇기에 멀티코어에서는 실제로 병렬로 작업이 동작할 수 있다.

UI 스레드에서 실행: Dispatchers.Main

UI를 사용할 떄 특정 작업을 UI 스레드나 메인 스레드라고 불리는 스레드에서 실행할 떄가 많다.

이런 작업을 실행할 떄 Dispatcher.Main을 사용할 수 있다.

Dispatcher.Main의 값을 프레임워크마다 다르다.

블로킹되는 IO 작업 처리: Dispatcher.IO

네트워크 I/O가 발생할 때 가령 DB작업시에는 실제로 스레드가 Blocking되기 때문에 Blocking되지 않게 I/O작업을 할 떄 마다 스레드 수를 늘려주는 풀을 사용한다. 하지만 최대 64개 까지 생성.

특수 디스패처와 커스텀 디스패처

코틀린 라이브러리는 위의 경우 외에 추가로 커스텀한 디스패처를 제공해준다.

예를 들어 Unconfined 디스패처는 특정 스레드에 제약되지 않고 코루틴을 실행되게 한다. 디스패처에 대한 병렬성 제약을 사용자 정의해야 하는 경우 limitedParallelism 함수를 사용할 수 있다. (동시성 문제를 해결하기 위해)

## 14.7.2 코루틴 빌더에 디스패처 전달

모든 코루틴 빌더 함수는 코루틴 Dispatcher를 전달할 수 있다.

```kotlin
fun main() {
	runBlocking {
		log("Do") // 메인 쓰레드
		launch(Dispatchers.Default) { // CPU 코어 수 쓰레드 풀
			log("Do some back") // 기본 디스패처 스레드 풀
		}
	}
}
```

## 14.7.3 withContext를 사용해 코루틴 안에서 디스패처 바꾸기

```kotlin
launch(Dispatcher.Default) {
	val result = performBackgroundOperation()
	withContext(Dipatchers.Main) { // 코루틴 빌더 안에서 dispatcher를 바꿀 수도 있다.
		updateUI(result)
	}
}
```

updateUI는 Main 디스패처에서 수행하게 한다.

## 14.7.4 코루틴과 디스패처는 Thread Safe 문제에 대한 해결책이 아니다.

Dispatchers.Default와 Dispatchers.IO 는 다중 스레드를 사용하는 기본 제공 디스패처이다.

그렇기에 멀티 스레드 환경에서 발생하는 Thread Safe 문제가 발생한다.

한 코루틴은 항상 순차적으로 실행된다. 단일 코루틴의 어떤 부분도 병렬로 실행되지 않는다. (당연히 스레드를 1개만 사용하니까). 그치만 코드라인이 블락되면 다른 함수가 코루틴을 수행할 수도 있다.

스레드 세이프 문제를 해결하기 위해 코루틴은 Mutex Lock을 제공하며, 이를 통해 임계 영역이 보장되게 한다

```kotlin
fun main() = runBlocking {
	val mutex = Mutex()
	var x = 0
	repeat(10_000) {
		launch(Dispatchers.Default) {
			mutex.withLock {
				x++
			}
		}
	}
	delay(1.seconds)
	println(x)
}
```

Lock말고 Atomic이나 Concurrent 패키지의 자료구조를 사용할 수도 있다.

## 14.8 코루틴은 코루틴 콘텍스트에 추가적인 정보를 담고 있다.

코루틴에서 실행되면 항상 coroutineContext를 갖고 있다.

Coroutine Context는 디스패처 정보, 생명주기, 예외시 취소를 관리하는 Job객체, Name, ExceptionHandler 등을 갖고 있다.

어떤 일시 중단 함수 안에서든 coroutineContext라는 특별한 속성에 접근할 수 있다.

또한 coroutineContext의 값을 바꾸거나 덮어쓸 수도 있다.

```kotlin
suspend fun introspect() {
	log(coroutineContext)
}

fun main() {
	runBlocking{
		introspect()
	}
}

// [CoroutineId(1), "coroutine#1" :BlockingCoroutine{Active}@1cd072a9, BlockingEventLoop@7c75222b]
```

덮어쓰기

```kotlin
fun main() {
	runBlocking(Dispatcher.IO + CoroutineName("Coolroutine")) {
		introspect()
	}
}
// [CoroutineName(Coolroutine) 이렇게 보임
```
