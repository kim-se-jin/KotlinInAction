# 정리
- 구조화된 동시성
  - 애플리케이션 안에서 코루틴과 그 생애주기의 계층을 관리하고 추적할 수 있는 기능
- 코루틴 스코프
  - 각 코루틴은 구조화된 동시성을 통해 코루틴 스코프에 속하게 됨
  - 코루틴 빌더의 본문에서 `launch`, `async`를 써서 새로운 코루틴을 만들면 자동으로 빌더 코루틴의 자식이 됨
  - 코루틴 간에는 부모-자식 관계가 있으므로 자식 코루틴의 완료를 기다릴 수 있음
- 코루틴 스코프 만들기
  - `coroutineScope` 함수
    - 일시 중단 함수
    - 새로운 코루틴 스코프를 생성하고 해당 영역 안의 모든 자식 코루틴의 완료를 기다림
    - 작업을 동시성으로 실행하기 위해 분해하는 데 사용
    - 예) 동시적 작업 분해: 여러 계산을 동시에 수행하고 결과를 전부 기다린 후 합치는 것
  - `CoroutineScope` 생성자 함수
    - 실행을 일시 중단하지 않음
    - 새로운 코루틴 스코프를 생성하기만 함
    - 코루틴을 클래스의 생명주기와 영관시키는 영역을 생성
    - 클래스 프로퍼티로 코루틴 스코프를 저장할 떄 주로 사용함
    - 대부분의 실무에서는 CoroutineScope와 SupervisorJob을 같이 사용하는 것을 권장
    - 자체 생명주기를 따르며 코루틴을 시작하고 관리할 수 있는 클래스를 만듦
  - `GlobalScope`
    - 전역 수준에 존재하는 코루틴 스코프
    - 사용 시 구조화된 동시성이 제공하는 모든 이점을 포기해야 함
    - 전역 코루틴은 자동으로 취소되지 않으며, 생명주기에 대한 개념도 없음
    - 리소스 누수, 자원 낭비 가능성
- 코루틴을 시작할 때 일어나는 일
  1. 자식 코루틴은 부모 코루틴의 콘텍스트를 상속받음
      - 디스패처를 지정하지 않고 새로운 코루틴을 시작하면 부모 코루틴의 디스패처에서 실행됨
  1. 새로운 코루틴은 `Job` 객체를 생성함 (코루틴간 부모-자식 관계 설정 등)
      - `job.parent`, `job.children` 등으로 확인 가능
  1. 코루틴 콘텍스트에 전달한 인자가 적용됨
- 코루틴 취소의 효능
  - 불필요한 작업을 막음
    - 사용자가 창을 닫거나 다른 화면으로 이동하는 경우
  - 메모리나 리소스 누수를 방지
  - 오류 처리
    - 동시적 작업 분해에서 하나가 실패하면 나머지는 결과를 기다리더라도 무의미한 경우
- 취소하기
  - 수동
    - 코루틴 빌더 함수의 반환값(Job, Deferred)의 cancel을 호출해 취소 가능
  - 자동
    - withTimeout, withTimeoutOrNull 등으로 시간 제한을 걸 수 있음
- 취소의 특징
  - 취소는 `CancellationException`을 던지는 방식으로 작동함
  - 취소된 코루틴은 일시 중단 지점에서 CancellationException을 던짐
  - 코루틴은 예외를 사용해 코루틴 계층에서 취소를 전파하기 떄문에 이 예외를 실수로 먹거나 직접 처리하지 않도록 주의해야 함
  - `catch(e: Exception)` 처럼 모든 예외를 퉁쳐서 잡지 않도록 주의
  - 코틀린 코루틴에 기본적으로 포함된 모든 함수는 취소 가능
  - 직접 작성한 코드에서는 직접 코루틴을 취소 가능하게 만들어야 함
- 코루틴이 취소되었는지 확인하기
  - CoroutineScope의 `isActive` 속성
  - `ensureActive` 편의 함수: 코루틴이 활성상태가 아니면 CancellationException 던짐
- 취소 가능 지점 만들기
  - `yield` 함수
  - 코드 안에서 CancellationException을 던질 수 있는 일시 중단 지점을 제공
  - 대기중인 다른 코루틴이 있다면 현재 점유된 디스패처에서 다른 코루틴이 작업할 수 있게 해줌
  - `isActive`, `ensureActive`는 '확인'을 하는거지 일시 중단 기회 자체를 주지 않음
- 외부 리소스와 취소
  - 취소는 다른 예외와 마찬가지로 코드의 조기 반환을 유발함
  - 코루틴이 취소되누 이후에도 리소스를 소유하지 않게 주의해야 함
  - 예) 디비 커넥션
  - `finally` 블록으로 예외 여부와 관계없이 리소스 반환 코드 작성하기
  - 리소스가 `AutoClosable` 인터페이스를 구현하는 경우 `.use` 함수를 사용하기
- 자동 취소
  - 현실에서는 프레임워크가 코루틴 스코프를 제공하고 취소를 자동으로 처리하는 경우가 많음
  - 안드로이드에서 사용자가 `ViewModel` 화면에서 벗어날 때 `viewModelScope`를 자동으로 취소함
  - HTTP 요청을 처리하는 라이브러리에서는 클라이언트가 연결을 끊으면 자동으로 취소함

# 궁금했던 것들
### 전역 코루틴은 왜 생명주기에 대한 개념이 없는 것일까?
- 설계 의도상 생명주기에 영향을 받지 않는 작업을 처리하기 위한 공간
- 코루틴 Job은 기본적으로 트리 형태인데, 전역 코루틴은 이 트리 구조에 속하지 않는 아예 별개의 공간에 있다고 할 수 있음
- 전역 스코프를 경계하는 이유: 관리되지 않는 루트 코루틴을 너무 쉽게 만들 수 있어서
- `coroutineScope`: 반드시 구조화된 동시성에 참가하겠다
- `CoroutineScope`: 구조화된 동시성에 참가할 수도 있고 아닐 수도 있다
- `GlobalScope`: 나는 구조화된 동시성 싫다

### CancellationException을 코루틴 계층의 취소 전파에 사용하면, 이건 코루틴 스코프 밖에서 잡아야 하는 것인가?
- 이 Exception은 정상적인 control flow에 가까우므로 리소스 정리, 로그, UI 변경 등 특수한 경우가 아니면 잡지 않는 것을 권장함

### `yield`로 일부러 일시 중단 지점을 만드는 예시를 실제 서비스를 만들 떄 사용하는 경우가 있을까?
- CPU 점유를 굉장히 오래 하는 작업의 경우 일부러 다른 작업에 양보하기 위해 사용하는 경우가 가끔 있다고 함
