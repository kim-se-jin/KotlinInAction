# 정리
- 플로우
  - 시간이 지남에 따라 나타나는 여러 값을 다루는 상황에서 코틀린의 동시성 매커니즘을 사용할 수 있게 해줌
  - 일시 중단 함수: 단일 값만 반환할 수 있기 때문에 모든 작업이 끝나고 하나의 값을 반환함
  - 함수가 여러 값을 시간이 지남에 따라 계산하는 상황에서, 함수가 실행을 마칠 때까지 기다리지 않고 값을 사용할 수 있도록 비동기적으로 반환하고 싶을 때 사용
  - 반응형 스트림과 비슷하게 점진적 로딩, 이벤트 스트림 작업, 발행-구독 모델 등에 사용 가능
- 플로우의 종류
  - 콜드 플로우
    - 비동기 데이터 스트림
    - 값이 실제로 소비되기 시작할 떄만 값을 배출함
  - 핫 플로우
    - 값이 실제로 소비되고 있는지와 상관없이 값을 독립적으로 배출
    - 브로드캐스트 방식으로 동작
- 콜드 플로우
  - `flow` 빌더 함수
    - 새로운 플로우를 생성
    - `Flow<T>` 타입의 객체를 반환
    - 처음에 비활성 상태이며, terminal operator 호출 이후에만 빌더의 람다가 수행됨
    - 처음에 비활성이므로 일시 중단 함수가 아니더라도 플로우 작성 가능
    - 처음에 비활성이므로 무한 플로우 작성 가능
  - `emit` 함수
    - 플로우의 수집자에게 값을 제공하고 수집자가 해당 값을 처리할 때까지 빌더 함수의 실행을 중단시킴
  - `collect` 함수
    - 플로우 실행
    - 플로우에서 배출된 각 원소에 대해 호출할 람다를 제공
    - collect 자체와 제공한 람다는 일시 중단 함수
- 콜드 플로우의 특징
  - 콜드 플로우에 대한 collect를 여러 번 호출하면 여러 번 실행됨
  - 네트워크 요청 등 부수 효과 역시 여러 번 실행될 수 있음에 주의
  - 수집자의 코루틴 취소 시 다음 취소 지점에서 플로우 수집 중단 (무한 플로우에 대한 대응)
  - 일시 중단 함수와 수신 객체 지정 람다를 결합해서 구현된 기능
    - collect 호출 시 flow 빌더의 본문 실행
    - flow 본문에서 emit 호출 시 그 값으로 collect 의 람다 호출
    - collect의 람다가 끝나면 빌더 함수 본문으로 돌아가 다음 작업 수행
- 채널 플로우
  - 콜드 플로우는 반드시 순차적으로 실행되는데, 플로우가 서로 독립적으로 실행될 수 있는 여러 작업을 수행할 떄 병목이 발생할 수 있음
    - 콜드 플로우는 같은 코루틴 안에서만 emit 호출 가능하게 허용하기 때문
  - 여러 코루틴에서 배출을 허용하는 플로우
  - `channelFlow` 빌더 함수
  - `send` 함수
    - 여러 코루틴에서 값을 제공
  - `collect`
    - 수집자는 여전히 값을 순차적으로 수신함
    - 하지만 여러 코루틴에서 동시다발적으로 값을 보내고 있기 떄문에 총 완료시간이 짧을 수 있음
- 채널 플로우는 무적인가?
  - 기본 콜드 플로우는 가장 간단하고 성능이 좋은 추상화
  - 채널 플로우는 채널 관리가 별도로 필요해서 추가 비용이 있음
  - 플로우 안에서 새로운 코루틴을 시작하는 경우에만 채널 플로우 선택하는 것을 권장함
- 핫 플로우
  - 배출된 항목을 여러 구독자가 공유하며 수신하는 형태
  - 시스템에서 이벤트나 상태 변경이 발생해서 수집자가 존재하는지 여부에 상관없이 값을 배출해야 하는 경우에 적합
  - 구독자가 존재 여부에 상관없이 배출: 브로드캐스트
  - 배출을 수행하는 코루틴의 시작 책임은 개발자에게 있음
  - `collect`
    - 구독자 추가
    - 구독 수신 이후에 배출된 값들만 수신함
  - `replay` 파라미터
    - 새로운 구독자를 위해 제공할 값의 캐시를 설정
    - 지난 값을 보여줄 수 있음
  - `shareIn` 함수
    - 콜드 플로우를 공유 플로우로 변환하고 발행을 시작
    - 플로우 수집의 시점을 즉시, 첫 번째 구독자 등장시, 구독자 없어지면 수집 종료 등의 옵션을 줄 수 있음
- 상태 플로우
  - 시간이 지남에 따라 변할 수 있는 값(=상태)을 추적
  - MutableStateFlow 를 내부적으로 상태를 변경시킬 속성으로 사용하고, StateFlow를 외부로 노출해서 값에 접근
  - 상태이므로 초깃값 필요
  - `update`
    - 원자적으로 상태를 변경
    - value 자체를 바꾸는 것은 thread-safe 하지 않아서 이 함수를 사용하는 것을 권장함
  - StateFlow의 value 속성으로 현재 값에 별도의 처리 없이 바로 접근 가능
  - 동등성 기반 통합: 실제 값이 바뀌었을 떄만 구독자에게 새로운 값을 배출
  - `stateIn` 함수
    - 콜드 플로우를 상태 플로우를 변환
    - 플로우에서 배출된 최신 값을 상태로 취급하여 항상 읽을 수 있음
- 상태 플로우 vs 공유 플로우
  - 공유 플로우
    - 구독자가 구독하는 동안만 이벤트를 배출
    - 구독자가 자유롭게 추가/삭제됨
  - 상태 플로우
    - '상태'를 나타냄
    - 동등성 기반 통합
  - 상태 플로우는 공유 플로우보다 API가 간단함
    - 공유 플로우를 사용하는 문제를 상태 플로우로 해결할 수 있을지에 대한 고려 필요
- 콜드 플로우 vs 핫 플로우
  - 콜드 플로우
    - 기본적으로 비활성
    - 수집자는 하나만 존재
    - 수집자가 모든 배출을 받음
    - 일반적으로 finite
    - 하나의 코루틴에서 배출하는 것이 일반적
    - 네트워크 요청이나 디비 읽기 같은 서비스는 콜드 플로우를 사용함
  - 핫 플로우
    - 기본적으로 활성
    - 여러 구독자 가능
    - 구독 시작 이후의 배출만 받음
    - 일반적으로 infinite
    - 여러 코루틴에서 배출 가능

### Q1) 일반 flow {} 빌더와 channelFlow {} 빌더의 내부 동작 차이는 무엇인가요? 왜 channelFlow가 더 무겁다고 할까요?
- channelFlow는 여러 코루틴에서 값의 발행을 허용
- 채널 플로우는 여러 채널 관리가 별도로 필요해서 추가 비용이 있음
  - 생산자와 소비자의 속도가 달라도 동작할 수 있게끔 별도의 큐를 두고 있음
