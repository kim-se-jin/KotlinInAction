# 17장 — 플로우 연산자 (Flow Operators)

---

## 17.1 플로우 연산자로 플로우 조작

플로우 연산자는 컬렉션 연산자와 모양이 같다. `map`, `filter`, `take` 등 이름도 익숙하다.
다른 점은 연산이 비동기 스트림 위에서, suspend 컨텍스트로** 일어난다는 것이다.

- 중간 연산자는 연결(chaining) 해서 파이프라인을 만든다.
- 파이프라인은 최종 연산자가 붙어야 실제로 흐른다.

---

## 17.2 중간 연산자는 업스트림 플로우에 적용되고 다운스트림 플로우를 반환한다

- **업스트림(upstream)**: 나보다 위쪽 — 값을 흘려보내는 쪽
- **다운스트림(downstream)**: 나보다 아래쪽 — 값을 받는 쪽

중간 연산자는 "업스트림에서 받아 → 가공해서 → 다운스트림으로 내보내는" 새 `Flow`를 만든다. 그게 전부다.

### 17.2.1 업스트림 원소별로 임의의 값을 배출: transform 함수

`map`은 원소 하나당 정확히 하나만 내보낼 수 있다(1:1).
`transform`은 원소 하나당 **원하는 만큼** `emit`할 수 있다(1:N, 0개도 가능).

```kotlin
namesFlow()
    .transform { name ->
        emit("$name 님 안녕하세요")   // 원소 하나에 대해
        emit("$name 님 반갑습니다")   // 두 번 배출
    }
    .collect { log(it) }
```

- 0개 emit → `filter`처럼 걸러내기
- 1개 emit → `map`처럼 변환
- 여러 개 emit → 하나를 여러 개로 펼치기

즉 `transform`은 `map`/`filter`를 포함하는 **가장 일반적인** 중간 연산자다.

### 17.2.2 take나 관련 연산자는 플로우를 취소할 수 있다

`take(n)`은 원소 n개를 받고 나면 **업스트림 플로우를 취소**한다. 그래서 무한 플로우도 안전하게 끊을 수 있다.

```kotlin
infiniteCounter()      // 끝없이 값을 내보내는 플로우
    .take(3)           // 3개만 받고 업스트림 취소
    .collect { log(it) }
```

- `take(n)` : 앞에서 n개만 받고 취소
- `takeWhile { }` : 조건이 참인 동안만 받고, 거짓이 되는 순간 취소

> 취소되면 업스트림 생산이 실제로 멈춘다(더 이상 `emit` 호출 안 됨). 자원 낭비가 없다.

### 17.2.3 플로우의 각 단계 후킹: onStart, onEach, onCompletion, onEmpty

플로우 생애주기의 특정 시점에 끼어들어 부수 효과(로깅, 자원 정리, 기본값 채우기)를 넣는다.

```kotlin
threeValues()
    .onStart      { log("수집 시작 직전 1번") }
    .onEach       { log("원소 통과: $it") }
    .onCompletion { cause -> log("종료 (정상/취소/예외 모두, cause=$cause)") }
    .onEmpty      { log("원소를 하나도 안 냈을 때만") }
    .collect { ... }
```

| 연산자 | 호출 시점 |
|--------|-----------|
| `onStart` | 수집이 시작되기 직전 1번 (첫 emit 전) |
| `onEach` | 원소가 하나 지나갈 때마다 |
| `onCompletion` | 플로우가 끝난 뒤 1번 — **정상 종료/취소/예외 모두** 포함 (원인은 `cause`) |
| `onEmpty` | 원소를 **하나도** 배출하지 않고 끝났을 때만 |

> `onStart`/`onEmpty` 블록 안에서도 `emit`으로 값을 추가로 흘려보낼 수 있다 (예: 빈 결과일 때 기본값 채우기).
> `onCompletion`은 `finally`처럼 취소/예외에도 반드시 불리므로 자원 정리에 적합하다.

### 17.2.4 다운스트림 연산자와 수집자를 위한 원소 버퍼링: buffer

기본 플로우는 **순차적**이다. 생산자가 `emit`하면 수집자가 그 값을 다 처리할 때까지 생산자는 멈춰서 기다린다(생산과 소비가 서로 발목을 잡음).

`buffer(n)`을 끼우면 생산자와 수집자가 **분리**된다.

```kotlin
fastProducer()
    .buffer()                  // 생산자는 버퍼에 넣고 곧장 다음 값 생산
    .collect {
        delay(300)             // 수집은 느리지만, 생산은 안 기다린다
        log("소비: $it")
    }
```

- 생산자는 버퍼에 값을 넣고 곧바로 다음 값을 만든다 (수집자를 기다리지 않음)
- 수집자는 자기 속도로 버퍼에서 꺼내 처리한다
- → 생산과 소비가 겹쳐서 전체 시간이 줄어든다 (**파이프라이닝**)
- **값을 버리지 않는다**(전부 보존). 버리는 건 `conflate`(17.2.5).

### 17.2.5 중간값을 버리는 연산자: conflate

`buffer`는 느린 수집자를 위해 값을 **모두 보관**한다.
`conflate`는 반대로, 수집자가 한 값을 처리하는 동안 새로 들어온 값으로 **덮어쓴다**. 다음에 가지러 오면 **그동안 쌓인 것 중 최신 값**만 받는다. 중간값은 버려진다.

```kotlin
fastNumbers()      // 0.1초마다 1~10
    .conflate()
    .collect {
        log("처리 시작: $it")
        delay(300)             // 처리하는 동안 들어온 중간값은 버려진다
        log("처리 완료: $it")
    }
// 1, 4, 6, 9, 10 처럼 건너뛰며 받는다 (정확한 값은 타이밍에 따라 다름)
```

| | `buffer` | `conflate` |
|---|---|---|
| 값 처리 | **다 보관**, 하나도 안 버림 | 처리 중 들어온 **중간값은 버림** |
| 받는 것 | 모든 값 | **최신 값**만 |
| 쓸 때 | 모든 값이 다 중요할 때 | 최신 상태만 중요 (실시간 진행률, 주가, 센서) |

### 17.2.6 일정 시간 동안 값을 필터링하는 연산자: debounce

`debounce(timeout)`은 값이 들어온 뒤 **timeout 동안 새 값이 없을 때만** 그 값을 통과시킨다. 빠르게 연달아 오는 값은 무시하고 "잠잠해진 뒤의 마지막 값"만 내보낸다.

```kotlin
searchQuery()       // k, ko, kot, kotl, ... 를 빠르게 타이핑
    .debounce(250)  // 250ms 동안 추가 입력이 없을 때만 통과
    .collect { log("검색 실행: \"$it\"") }
```

전형적 사용처는 **검색창 자동완성**이다. 매 글자마다 검색하지 말고, 타이핑이 멈춘 뒤 한 번만 검색한다.

> `conflate`가 "수집자 속도"에 맞춰 버린다면, `debounce`는 "시간(정적 구간)"을 기준으로 버린다.

### 17.2.7 플로우가 실행되는 코루틴 콘텍스트를 바꾸기: flowOn

기본적으로 플로우는 `collect`를 호출한 코루틴의 콘텍스트(스레드)에서 전부 실행된다.
`flow {}` 블록 안에서 직접 `withContext`로 스레드를 바꾸는 것은 **금지**되어 있다(예외 발생).

대신 `flowOn(dispatcher)`을 쓴다. `flowOn`은 **자기보다 위쪽(업스트림)** 연산만 지정한 디스패처에서 실행시킨다. 아래쪽(다운스트림)과 `collect`는 영향받지 않는다.

```kotlin
numbers()
    .map { it * 10 }          // ─┐ flowOn 위쪽
    .flowOn(Dispatchers.IO)   // ─┘ 여기까지를 IO 스레드에서 실행
    .map { it + 1 }           // ─┐ flowOn 아래쪽
    .collect { log(it) }      // ─┘ collect 의 콘텍스트(예: main)에서 실행
```

이를 **콘텍스트 보존(context preservation)** 규칙이라 한다: 어디서 실행될지가 호출 위치로 결정된다. 무거운 생산/변환을 백그라운드로 빼는 데 쓴다.

## 17.3 커스텀 중간 연산자 만들기

중간 연산자는 특별한 API가 아니다. **업스트림 `Flow`를 받아 새 `Flow`를 돌려주는 확장 함수**일 뿐이다. `flow {}` 안에서 업스트림을 `collect`하고, 원하는 대로 가공해 `emit`하면 그게 곧 나만의 연산자다.

```kotlin
fun <T, R> Flow<T>.myOp(): Flow<R> = flow {
    collect { value ->        // 업스트림에서 받아서
        emit(가공(value))      // 다운스트림으로 내보낸다
    }
}
```

예제에서는 두 개를 직접 만든다.

```kotlin
// 직전 N개의 평균
fun Flow<Double>.movingAverage(windowSize: Int): Flow<Double> = flow {
    val window = ArrayDeque<Double>()
    collect { value ->
        window.addLast(value)
        if (window.size > windowSize) window.removeFirst()
        emit(window.average())
    }
}
```

## 17.4 최종 연산자는 업스트림 플로우를 실행하고 값을 계산한다

중간 연산자는 새 플로우를 돌려줄 뿐 **아무것도 실행하지 않는다.** 실제로 업스트림을 돌게 만드는 것이 **최종(터미널) 연산자**다. 최종 연산자는 `suspend` 함수이고, 플로우를 끝까지 수집해 값 하나 또는 컬렉션을 만든다.

```kotlin
oneToFive().toList()                       // [1,2,3,4,5]
oneToFive().first()                        // 1   (받고 나면 업스트림 취소)
oneToFive().reduce { acc, v -> acc * v }   // 120 (초기값 없이 누적)
oneToFive().fold(100) { acc, v -> acc + v }// 115 (초기값 100 에서 누적)
```

| 최종 연산자 | 결과 |
|-------------|------|
| `collect { }` | 가장 기본. 원소마다 동작 수행 |
| `toList()` / `toSet()` | 모든 원소를 컬렉션으로 |
| `first()` / `single()` | 한 원소만 (받고 나면 업스트림 취소) |
| `reduce { }` | 초기값 없이 누적해 하나로 |
| `fold(init) { }` | 초기값을 두고 누적 |
| `count()` | 원소 개수 |

### 17.4.1 프레임워크는 커스텀 (최종) 연산자를 제공한다

`launchIn(scope)`은 **새 코루틴에서 수집을 시작시키는** 최종 연산자다. 보통 처리 로직은 `onEach`로 붙이고 `launchIn`으로 "발사"한다.

```kotlin
flow
    .onEach { log("수집: $it") }   // 처리 로직은 onEach 로
    .launchIn(scope)                // scope 에서 별도 코루틴으로 발사 → Job 반환

// 위 한 줄은 아래와 같다:
scope.launch { flow.collect { log("수집: $it") } }
```

`launchIn`은 값을 반환하지 않고 `Job`을 돌려준다. 안드로이드(`collectAsState`, `repeatOnLifecycle`)나 스프링 등 **프레임워크는 자신의 환경에 맞는 커스텀 (최종) 연산자**를 추가로 제공한다.
