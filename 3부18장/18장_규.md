# 정리
- 코루틴 내부의 오류 처리
  - 코루틴 빌더가 생성한 코루틴에서 발생한 예외는 빌더 밖의 catch 블록으로 잡을 수 없음
  - launch에 전달되는 람다 안에 try catch를 하면 잡을 수 있음
  - 자식 코루틴은 잡히지 않은 예외를 무조건 부모 코루틴에 전파함
  - 부모 코루틴은 자식 코루틴의 예외를 처리할 책임이 있음
- 코루틴의 오류 전파
  - 자식 코루틴을 처리하는 방식은 부모 코루틴 콘텍스트의 job 에 따라 달라짐
  - Job
    - 자식 코루틴에서 예외 발생 시
      - 다른 모든 자식을 취소
      - 같은 예외를 발생시키면서 자신을 종료
      - 자신의 상위 계층으로 예외를 전파
    - 형제를 취소시키는 기능은 일반적으로는 없음. 코루틴의 장점.
    - 같은 스코프 안에서 동시성 계산을 함께 수행하고 하나의 결과를 계산해서 반환할 경우 유용
    - 불필요한 작업을 피하고 자원을 해제함
    - 모든 코루틴 빌더는 일반적으로 Job을 사용하므로 자동으로 자식 코루틴들을 취소시킴
    - 코루틴 스코프 내에서 예외를 처리하게 하면 한 자식의 실패가 그 형제들을 실패시키지 않음
      - 예외 처리 시 CancellationException 을 잡지 않도록 주의.
  - SupervisorJob
    - 일부 자식이 실패하더라도 실패하지 않음
    - 다른 자식 코루틴을 취소시키지 않고 예외를 구조적 동시성 계층 상위로 전파하지 않음
  - CoroutineExceptionHandler
    - 자식 코루틴의 예외는 슈퍼바이저에 도착하거나 루트 코루틴에 도달하면 전파되지 않음
    - 이 시점에서 처리되지 않은 예외는 CoroutineExceptionHandler에게 전달됨
    - 코루틴 콘텍스트에 예외 핸들러가 없다면 처리되지 않은 예외는 시스템 전역 예외 핸들러로 이동함
    - 처리되지 않은 예외를 처리하는 동작을 커스텀화할 수 있음
    - 코루틴은 처리되지 않은 예외의 처리를 부모에게 위임하므로 중간에 있는 코루틴 콘텍스트에 이 핸들러를 정의했다면 무시됨.
    - 이 핸들러는 최상위 코루틴이 launch로 생성된 경우에만 호출됨.
    - 최상위 코루틴이 async인 경우 예외 처리의 책임은 await을 호출한 쪽에 있으므로 거기서 try catch 해야 함.
- 플로우에서의 예외 처리
  - 플로우의 일부분애서 예외가 발생하면 collect 에서 예외가 터짐
  - catch
    - 플로우에서 발생한 예외를 처리할 수 있는 중간 연산자
    - 코루틴의 취소 예외를 자동으로 인식하고 무시함
    - emit이 가능해서 예외 발생 시 원하는 값을 다운스트림 플로우에 전달할 수도 있음
    - 업스트림에서 발생한 예외를 감지함
  - retry
    - 업스트림에서 발생한 예외를 감지함
    - 재시도를 하면 업스트림 플로우를 처음부터 더시 수집하면서 모든 중간 연산을 다시 실행함
    - 부수 효과를 일으키는 작업을 수행하는 경우 멱등성을 보장할 수 있도록 할 것
- 코루틴 테스트
  - runTest
    - runBlocking은 테스트를 실시간으로 진행하며 모든 delay같은걸 기다리므로 테스트가 느려짐
    - 가상 시간을 사용해 테스트 실행을 빠르게 진행할 수 있음
    - 단일 스레드를 사용하는 특별한 디스패처와 스케줄러를 사용함
      - 코드 내에서 일시 중단 지점을 제대로 제공하고 있는지 확인하기
    - 테스트 디스패처가 아닌 디스패처들은 지연을 전부 기다리므로 테스트를 제대로 하고 싶으면 디스패처를 주입받을 수 있는 코드를 작성하는 것이 편함
- 플로우 테스트
  - 유한 플로우는 toList 등으로 모든 원소를 뽑아낸 후 바교하면 됨
  - Turbine 과 같은 외부 테스팅 라이브러리 사용을 추천

# 궁금했던 것들
### ExceptionHandler에서 throw 하면 시스템 전역 예외 핸들러로 가는지?
- 예외 핸들러의 예외는 현재 스레드의 전역 예외 핸들러로 넘어감
- 예외 핸들러에서 예외를 발생시키는 것은 권장하지 않음

### launch vs async? 반환값 유무 차이였던것 같음
- fire and forget 이냐 결과물을 필요로 하냐의 차이

### flow의 retry는 플로우를 아예 처음부터 수집하는데 중간저장 시스템은 따로 없는 것인지?
- flow 자체는 상태를 기억하지 않음
- 외부에 별도로 상태를 두어 중간 지점을 관리하거나, 재실행에도 영향을 받지 않도록 멱등성을 보장하는 코드를 작성하는 것이 필요함
