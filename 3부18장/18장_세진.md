# 18장. 오류 처리와 테스트

## 18.1 코루틴 내부에서 던져진 오류 처리

- 코루틴 안에서 예외 발생 시
  - `try-catch`로 잡을 수 있다.

```kotlin
suspend fun fetchData() {
    try {
        val result = riskyOperation()
        println(result)
    } catch (e: Exception) {
        println("오류 발생: ${e.message}")
    }
}
```

- 코루틴은 비동기적으로 실행되기 때문에, 예외가 발생한 지점과 그 예외를 처리할 수 있는 지점이 다를 수 있다는 점!
- `launch`로 시작된 코루틴 내부의 예외는
  - 호출한 쪽에서 즉시 `try-catch`로 잡을 수 없다.
    - `launch`는 코루틴을 시작하고 즉시 반환하기 때문
    -  예외는 `launch`를 호출한 코드 흐름이 아니라 새로 생성된 코루틴 내부에서 발생하여, Job 계층을 통해 별도의 경로로 전파됨

```kotlin
fun main() = runBlocking {
    try {
        launch {
            throw IllegalStateException("문제 발생")
        }
    } catch (e: Exception) {
        // 여기서 잡히지 않는다!
        println("잡았다: ${e.message}")
    }
}
```


   `async`의 경우 예외는 `Deferred` 안에 저장되었다가 `await()`를 호출할 때 다시 던져짐

```kotlin
fun main() = runBlocking {
    val deferred = async {
        throw IllegalStateException("문제 발생")
    }
    try {
        deferred.await() // 여기서 예외가 던져짐
    } catch (e: Exception) {
        println("잡았다: ${e.message}")
    }
}
```

## 18.2 코틀린 코루틴에서의 오류 전파

### 18.2.1 자식이 실패하면 모든 자식을 취소하는 코루틴

- 자식 코루틴 중 하나가 예외로 실패 시, 그 예외는 부모로 전파되고 부모는 나머지 모든 자식을 취소함

```kotlin
fun main() = runBlocking {
    launch {
        launch {
            delay(100)
            throw IllegalStateException("자식1 실패")
        }
        launch {
            delay(1000)
            println("자식2 완료") // 실행되지 않음
        }
    }
}
```
---

### 18.2.2 구조적 동시성은 코루틴 스코프를 넘는 예외에만 영향을 미친다

```kotlin
suspend fun doWork() = coroutineScope {
    launch {
        throw IllegalStateException("실패")
    }
}

fun main() = runBlocking {
    try {
        doWork()
    } catch (e: Exception) {
        println("잡았다: ${e.message}") // 여기서 잡힌다
    }
}
```

- `coroutineScope` 내부에서 발생한 예외는 `coroutineScope`를 호출한 코드로 다시 던져짐
  - `launch`의 예외가 부모 Job 계층을 통해 전파되는 것과는 다른 경로 !!
- `coroutineScope`는 내부에서 발생한 실패를 캡슐화해서 호출자에게 일반적인 예외처럼 전
- `coroutineScope`로 감싼 코드는 그 안에서 일어나는 일을 외부 코루틴 계층으로부터 격리시키면서도, 일반적인 `try-catch`로 결과를 처리할 수 있음

---

### 18.2.3 슈퍼바이저는 부모와 형제가 취소되지 않게 한다

- `SupervisorJob`을 사용하면 자식 코루틴의 실패가 부모나 다른 형제 코루틴에 전파되지 않음

```kotlin
fun main() = runBlocking {
    val scope = CoroutineScope(SupervisorJob())

    scope.launch {
        delay(100)
        throw IllegalStateException("자식1 실패")
    }

    scope.launch {
        delay(1000)
        println("자식2 완료") // 정상적으로 실행됨
    }

    delay(2000)
}
```

- `SupervisorJob`을 직접 콘텍스트로 넘기는 방식과 자식 코루틴의 콘텍스트에 `SupervisorJob`을 직접 지정하는 방식은 동작이 다르므로 유의하자

```kotlin
// 잘못된 사용: 이렇게 하면 SupervisorJob의 효과가 없다
launch(SupervisorJob()) {
    launch {
        throw IllegalStateException()
        // 이 launch는 바깥 launch의 자식이지,
        // SupervisorJob의 직접적인 자식이 아니다
    }
}
```

## 18.3 CoroutineExceptionHandler: 예외 처리를 위한 마지막 수단

- `CoroutineExceptionHandler`: 예외가 부모로 모두 전파되어 더 이상 처리할 곳이 없을 때 호출되는 최종 처리기

```kotlin
val handler = CoroutineExceptionHandler { context, exception ->
    println("처리되지 않은 예외: ${exception.message}")
}

fun main() = runBlocking {
    val scope = CoroutineScope(Job() + handler)
    scope.launch {
        throw IllegalStateException("문제 발생")
    }
    delay(100)
}
```

- `CoroutineExceptionHandler`는 코루틴 콘텍스트의 요소로 추가됨
- 이 핸들러는 루트 코루틴(부모가 없는 최상위 코루틴)의 콘텍스트에 설치되어야 동작
  - 예외가 부모로 전파되는 과정에서 핸들러를 찾는 위치가 루트이므로, 자식 코루틴에 설치하면 효과X

```kotlin
// 효과 없음: 자식에 설치
scope.launch {
    launch(handler) { // 여기 설치해도 부모로 예외가 먼저 전파됨
        throw IllegalStateException()
    }
}

// 올바름: 스코프 생성 시 루트에 설치
val scope = CoroutineScope(Job() + handler)
```

---

### 18.3.1 CoroutineExceptionHandler를 launch와 async에 적용할 때의 차이점

- `launch`에서 발생한 예외는 즉시 부모로 전파되고, `CoroutineExceptionHandler`가 설치되어 있으면 거기서 처리됨

```kotlin
val handler = CoroutineExceptionHandler { _, e ->
    println("launch 예외 처리: ${e.message}")
}

val scope = CoroutineScope(Job() + handler)
scope.launch {
    throw IllegalStateException("launch 실패")
}
```

- `async`에서 발생한 예외는 `Deferred` 안에 저장되고, `await()`가 호출되기 전까지는 던져지지 X
  - `async`가 결과값을 반환하는 빌더이기 때문에 발생
  - `CoroutineExceptionHandler`가 설치되어 있어도 `await()`를 호출하지 않으면 핸들러가 호출되지 않을 수 있음
  - 예외 처리의 책임이 `await()`를 호출하는 쪽으로 위임되는 구조
  - 최상위 `async`를 사용할 때는 반드시 `await()`를 호출하거나, `try-catch`로 감싸야 예외를 놓치지 않는다 !!!!

## 18.4 플로우에서 예외 처리

### 18.4.1 catch 연산자로 업스트림 예외 처리

- 플로우 전용 연산자인 `catch()`를 사용하는 것이 더 관용적

```kotlin
flow {
    emit(1)
    emit(2)
    throw IllegalStateException("플로우 오류")
    emit(3) // 실행되지 않음
}
    .catch { e ->
        println("예외 처리: ${e.message}")
        emit(-1) // 예외 발생 시 대체 값 배출 가능
    }
    .collect { println(it) }
// 출력: 1, 2, 예외 처리: 플로우 오류, -1
```

- `catch()`의 핵심 특징은 업스트림에서 발생한 예외만 잡는다
- `catch()` 아래쪽(다운스트림)에서 발생한 예외, 즉 `collect` 블록 안에서 발생한 예외는 잡지 못한다

```kotlin
flow { emit(1) }
    .catch { e -> println("여기서는 못 잡음") }
    .collect {
        throw IllegalStateException("collect에서 발생")
        // catch()가 위에 있어도 이 예외는 잡히지 않는다
    }
```

이 예외를 잡으려면 `catch()`를 `collect` 다음에 두거나, `onEach`로 옮겨서 `catch()`가 그 예외도 업스트림으로 취급하게 만들어야 한다.

```kotlin
flow { emit(1) }
    .onEach {
        throw IllegalStateException("여기서 발생")
    }
    .catch { e -> println("이제 잡힌다: ${e.message}") }
    .collect()
```

---

### 18.4.2 술어가 참일 때 플로우의 수집 재시도: retry 연산자

- `retry()`: 업스트림에서 예외가 발생했을 때 지정한 조건에 따라 플로우 수집을 다시 시도

```kotlin
var attempt = 0

flow {
    attempt++
    println("시도: $attempt")
    if (attempt < 3) {
        throw IOException("네트워크 오류")
    }
    emit("성공")
}
    .retry(retries = 2) { e ->
        e is IOException // 이 조건이 참일 때만 재시도
    }
    .collect { println(it) }
// 출력:
// 시도: 1 (실패)
// 시도: 2 (실패)
// 시도: 3 (성공)
// 성공
```

- `retry()`는 업스트림 플로우 블록을 처음부터 다시 실행함
- 이미 배출된 값을 기억하고 이어서 진행하는 것이 아니라, 플로우 전체를 재시작

`retryWhen()`을 사용하면 더 정교한 재시도 로직(예: 지수 백오프)을 구현할 수 있다.

```kotlin
flow { /* ... */ }
    .retryWhen { cause, attempt ->
        if (cause is IOException && attempt < 3) {
            delay(1000 * (attempt + 1)) // 지수적으로 대기 시간 증가
            true // 재시도
        } else {
            false // 재시도 중단
        }
    }
```

## 18.5 코루틴과 플로우 테스트

### 18.5.1 코루틴을 사용하는 테스트를 빠르게 만들기: 가상 시간과 테스트 디스패처

- `kotlinx-coroutines-test` 라이브러리는 가상 시간(virtual time)을 사용해 `delay` 무시 가능
- `runTest`는 테스트 전용 코루틴 빌더로, 내부의 `delay()` 호출을 실제로 기다리지 않고 즉시 진행시킨다.

```kotlin
@Test
fun testMultipleDelays() = runTest {
    val results = mutableListOf<Int>()

    launch {
        delay(100)
        results.add(1)
    }
    launch {
        delay(200)
        results.add(2)
    }

    advanceUntilIdle() // 모든 가상 시간을 진행시켜 모든 코루틴 완료
    assertEquals(listOf(1, 2), results)
}
```

- `advanceTimeBy()`로 특정 시간만큼만 가상 시간 진행
- `advanceUntilIdle()`로 대기 중인 모든 작업이 끝날 때까지 진행
- `TestDispatcher`를 직접 사용해 디스패처를 교체하는 패턴
  -  `Dispatchers.IO`나 `Dispatchers.Default`를 사용하는 부분을 테스트 시에는 `TestDispatcher`로 주입해 테스트 환경에서 결정적으로 동작하도록

### 18.5.2 터빈으로 플로우 테스트

- 터빈(`Turbine`): `Flow`, 특히 `StateFlow`나 `SharedFlow` 같은 핫 플로우를 테스트할 때는 값이 여러 번 배출되는 순서를 검증해야 하는 경우가 많은데, 이를 쉽게 해주는 서드파티 라이브러리

```kotlin
@Test
fun testFlow() = runTest {
    val flow = flowOf(1, 2, 3)

    flow.test {
        assertEquals(1, awaitItem())
        assertEquals(2, awaitItem())
        assertEquals(3, awaitItem())
        awaitComplete()
    }
}
```

- `test { }` 블록 안에서 `awaitItem()`으로 다음 배출 값을 순서대로 검증하고, `awaitComplete()`로 플로우가 정상 종료되었는지, `awaitError()`로 예외가 발생했는지 확인 가능

- `StateFlow`나 `SharedFlow`처럼 계속 살아있는 핫 플로우를 테스트할 때도 유용

- 내부적으로 별도의 코루틴을 사용해 플로우를 구독하고, 배출된 값을 큐에 담아 `awaitItem()` 호출 시점에 꺼내주는 방식으로 동작
  - 테스트가 끝날 때 구독이 자동으로 취소되므로 코루틴 누수도 신경 쓰지 않아도 된다는 점!
